# Cohaera and the Exabeam agent-monitoring stack

For someone who already ships agent monitoring and wants to know, in ten
minutes, whether there is anything here worth their time.

[POSITIONING.md](../POSITIONING.md) records the correction this project had to
make once Exabeam's Agent Behavior Analytics shipped. This document extends
that correction to the rest of the stack — the sponsored open-source projects,
the normalisation standards, and the pre-deployment verifier — and states what
is left over. It concedes more than it claims, on purpose.

**On sourcing.** Every claim below is either verified from a public GitHub
repository, quoted with its path, or marked as reported and not independently
verified. Vendor domains including `exabeam.com` are unreachable from the
environment this was written in; those URLs are cited so you can check them
yourself. The full split is in
[the sources table](#sources-verified-versus-reported) at the end.

---

## 1. The numbers, before anything else

Read these first. They are the reason to stop reading, if you are going to.

| | |
|---|---|
| False positives | **420.4 per 1,000 benign sessions** |
| Projected precision at a 0.1% attack base rate | **0.238%** |
| Catalogued evasions | 22 constructed, **20 still work**, each with a passing test |
| Corpus | Synthetic, generated by the same author as the detector |
| External validation | **None.** No live SIEM, no independent labels, no second reviewer |
| Status | Pre-alpha research artifact |

At a realistic base rate almost every alert this produces is benign. That is
not a tuning problem to be waved at; it is the headline result, and
[`eval/EVALUATION-CARD.md`](../eval/EVALUATION-CARD.md) is generated rather
than written so it cannot quietly improve.

Nothing in the rest of this document should be read as a claim that Cohaera
detects attacks well. The argument is narrower than that, and section 6 states
it in one sentence.

## 2. The layer map

Five layers and one orthogonal axis. Cohaera occupies one row.

| Layer | What it answers | Who does it |
|---|---|---|
| Collection | What did the agent emit? | observra, agent sensors, OTel SDKs |
| Semantic normalisation | What do the fields mean? | observra's CIM, ASIM, OTel GenAI semconv |
| **Evidence quality** | **Does this record deserve to be believed, and which questions could not be answered at all?** | **Cohaera** |
| Behavioural analytics | Was this normal for this agent? | Exabeam Agent Behavior Analytics |
| Investigation and response | What do we do about it? | The SIEM |

Off to the side, on a different axis entirely:

| Axis | What it answers | Who does it |
|---|---|---|
| Pre-deployment verification | Is the agent *built* to do only its job? | Praxen |

Praxen is not a layer in that stack. It runs at a different point in the
lifecycle and consumes different inputs. Praxen's own documentation makes the
same split, and names both halves:

> **Agent Behavior Verification (ABV)** defines and verifies expected behavior
> **before deployment**.
>
> **Agent Behavior Analytics (ABA)** observes behavior **after deployment** —
> runtime visibility, behavioral baselining, drift detection, anomaly
> identification, and operational oversight of deployed agents.
>
> — [`docs/abv.md`](https://github.com/open-agent-ai-security/praxen/blob/main/docs/abv.md),
> `open-agent-ai-security/praxen`

The same page gives a six-step lifecycle: define the role, verify the
implementation, deploy, **observe runtime behaviour**, detect drift and misuse,
refine. Cohaera's entire claim is a precondition on step 4. Observation is
treated there as a primitive. It is not one when the observer runs inside the
observed process.

### Two things the map concedes

**Normalisation is not winnable and Cohaera should stop implying otherwise.**
The OpenTelemetry GenAI semantic conventions now have their own repository,
covering model spans, agent spans, events, metrics and MCP. All five documents
are marked `Status: Development`. In `docs/gen-ai/gen-ai-agent-spans.md` the
stability badges run 202 Development against 14 Stable — and every Stable badge
belongs to a borrowed core attribute (`error.type`, `server.address`,
`server.port`) or to the `_OTHER` enum fallback. Not one `gen_ai.*` attribute
is stable. That is an unfinished standard, not an absent one, being finished by
a working group with more claim to it than this project has. Microsoft is
reported to ship an `AI Agent Events` ASIM schema in Sentinel; I could not
verify that from here and it does not change the conclusion. Cohaera consumes
normalised evidence and should not be sold as producing it.

**The collector runs inside the agent.** Placing observra at collection
understates its own claim — its README headline is "Framework-agnostic agent
behavior analytics" and it ships built-in prompt-injection heuristics. The row
stands anyway, and not on a reading of the marketing:
[FINDINGS.md](../FINDINGS.md) records, file and line, that `evaluate_rules` has
the signature `(event_type, data)` and cannot see two events, that
`velocity.py` computes a rate and compares it to nothing, and that the
architecture pipeline has no analysis stage. The maintainer's own issue #108
(4 Aug 2026) says "28/34 AI analytics rules work today. Zero correlation rules
can fire." A scope boundary, stated upstream, not a defect.

What matters more here is where the collector sits. observra attaches to the
agent framework as an in-process plugin — its quick start says so in the code
comment, `plugins=[plugin],  # the only change — telemetry is now automatic`.
That is the right engineering decision for a collector and exactly what makes
the evidence-quality question non-trivial. Its feature list covers PII
redaction, encryption at rest, deduplication and non-blocking delivery:
confidentiality and reliability controls. As of the README on `main`, the words
*signature*, *integrity*, *tamper*, *provenance* and *hash* do not appear in it
at all. A collector is not obliged to attest to its own output — that is an
observation about scope, not a defect.

## 3. Praxen, stated precisely

Praxen is Apache-2.0, in the `open-agent-ai-security` org, and its README says:

> Praxen is sponsored by [Exabeam](https://www.exabeam.com/). Exabeam
> contributed the initial code and continues to provide ongoing support and
> contributions to the project.

Its one-line description is **agent behavior verifier**, and its stated job is
comparing an agent's declared policy — the Worker Remit — against the available
evidence, reporting where observed behaviour diverges from declared intent.
Evidence, in Praxen's sense, is "source code, deployment state, behavioral logs,
governance docs, or any mix."

The boundary is Praxen's own, in its README, unprompted:

> Praxen runs **before deployment** and on each release — pre-deployment
> verification of the agent's controls against its remit. Runtime monitoring of
> the deployed agent is a complementary layer outside Praxen's scope.

So the relationship is not contested. Praxen asks whether the agent is built to
do only its job. Cohaera asks whether the runtime record of what it did
deserves to be believed. Praxen's README does not discuss evidence quality,
telemetry trustworthiness, or reporting what could not be evaluated — the one
occurrence of "coverage" in it refers to OWASP framework coverage grids, not to
whether a check had the inputs to run.

One further difference, offered as complementarity rather than criticism.
Praxen is a model-assisted expert review, run as a skill inside a frontier-model
coding agent; its own docs say scores vary run to run and should be read as "a
senior reviewer's notes, not an automated pass/fail". Cohaera is deterministic:
same input, same verdict, byte-identical evaluation card on the same revision.
Different tools for different questions.

### The risk, said plainly

That gap is one roadmap item wide.

Exabeam sponsors the collector, defines the CIM the events are normalised
against, ships the analytics that consume them, and now sponsors a third project
(`socxen`, an agentic SOC skill suite for Exabeam New-Scale, currently marked
Incubator and pre-release) that puts agents inside the investigation workflow
too. An organisation holding all four positions can add evidence-integrity
fields to its own collector, a coverage field to its own CIM, and a
"could-not-evaluate" state to its own analytics, without asking anyone. There
is no moat here, and claiming one would be the second time this project
mistook an unoccupied position for a defensible one.

What is on offer is a head start and a set of negative results, not a
technology nobody else can build. If that is not worth ten minutes, the honest
answer is that it might not be.

## 4. What Cohaera does not do

Stated before you have to ask.

- **Behavioural baselining.** ABA does this. Cohaera has no entity model, no
  peer groups, no first-time-seen logic, and no risk accumulation. It fits a
  bigram baseline over benign sessions and that is the extent of it.
- **Long-horizon entity risk.** Nothing here spans users, applications or
  identities. There is no entity at all beyond an agent string.
- **Cross-session reasoning of any kind.** Sessions are scored independently.
  Evasion E08 — split the read and the act across two sessions — is catalogued
  as working, for exactly this reason.
- **Normalisation as a differentiator.** See section 2.
- **Anything that has been externally validated.** The corpus is synthetic and
  written by the detector's author. The evaluation card's own limitations
  section calls the numbers "an upper bound on a lower bound".

And the numbers from section 1 apply to all of it: 420.4 false positives per
1,000 benign sessions, 0.238% projected precision at a 0.1% base rate, 20 of 22
catalogued evasions still working.

## 5. The one asymmetry worth a look

This is the part that is not in the README's opening screen and probably should
be. It is currently in §4 of the evaluation card.

Cohaera's seven checks do not behave like one detector. They split cleanly:

| Check | What it does | On its own attacks | On benign | Target precision |
|---|---|---|---|---|
| `CH01_sequence_order` | sequence novelty | 72 | 60 | 35.3% |
| `CH02_concealment_gap` | disclosure gap | 52 | 108 | 27.1% |
| `CH03_untrusted_to_consequential` | influence path | 32 | 48 | 40.0% |
| `CH05_unpaired_calls` | missing terminals | 0 | 48 | 0.0% |
| **`CH04_guardrail_overrun`** | **control fired, action proceeded** | **72** | **0** | **100.0%** |
| **`CH06_evidence_integrity`** | **chain, key trust, freshness** | **56** | **0** | **100.0%** |
| **`CH07_effect_contradiction`** | **claimed failure, provider receipt** | **16** | **0** | **100.0%** |

The four behavioural checks account for every benign alert in the corpus. The
three bolded ones account for none — including against 200 benign confounder
sessions built specifically to break them: an ADVISORY threshold legitimately
continued past (48), a properly approved continuation of a blocking control
(28), a re-approved retry after a failure (28), records delivered out of order
by a streaming path (24), and a collector key rotation with one session
straddling the handover (72). Zero false positives across all of them.

The reason is structural, not statistical. Those three are deterministic
verifiers, not behavioural detectors. There is no baseline to fit, no learning
period, no drift, no per-tenant tuning. Either the chain is continuous or it is
not; either the approval names the arguments that executed or it names
different ones; either the provider-returned identifier exists on a call the
agent reported as failed or it does not. Reruns are byte-identical.

The most instructive of the three is CH04, and it is instructive because
*nothing about the detection changed*. It went from 50% alert precision to
100%, and its largest single false-positive source went to zero, because a
field appeared saying whether the control was advisory or blocking. A check
that had been reporting a sequence because it could not report a bypass stopped
having to. That is a data-contract result, not a detection result, and it is
the strongest single argument in this repository for section 6.

### Why that table is not as good as it looks

Zero false positives is a statement about the benign side only. The adversarial
side has its own table and it is not flattering:

| Evasion | Target | Cost to attacker |
|---|---|---|
| E10 `working` | CH04 | act before the threshold trips — free |
| E20 `half_closed` | CH04 | declare a blocking control `advisory` on the event — one string |
| E23 `half_closed` | CH03, CH04 | stamp the consequential call on the control's own tick — one field |
| E22b `working` | CH06 | replay the stream to a different Cohaera host — the ledger is per-host |

Two further caveats the evaluation card raises against itself. CH06 and CH07
only reach `evaluated` where sidecar formats exist that essentially nobody
emits yet; across most of the corpus CH06 reports `degraded`, which is the
realistic first-adoption state. And one of CH06's attack rows —
`attack_revoked_key_stream`, 32 of 32 — is close to a tautology: it looks a key
id up in an operator-supplied file and finds `revoked_at` set. The row that
could have failed is the benign one, 0 of 72 on a correct rotation.

So the claim is not "these three checks are good". It is that they are a
different *kind* of check from the other four, they fail in different ways, and
a stack that mixes them without saying which is which will misattribute both
their successes and their noise.

## 6. If you take one idea, take this one

**A check that cannot run must be forbidden from returning clean.**

Configuration assessment worked this out long ago, and the useful form of it is
not one extra status but a three-way refusal to assert. The OVAL results schema
keeps these apart, in `ResultEnumeration`:

| Value | What the schema says it means |
|---|---|
| `not evaluated` | "a choice was made not to evaluate the given definition or test. The actual result is not known since if evaluation had occurred the result could have been either true or false" |
| `unknown` | "the characteristics being evaluated cannot be found in the system characteristic document… there is no way of knowing what the result would be if the file was collected" |
| `not applicable` | "the definition or test being evaluated is not valid on the given platform" |

Three different reasons a result was not produced, none of them collapsed into
`true` and none into `false`. (The 5.11 schema carries a Center for Internet
Security copyright and points at `oval.cisecurity.org`, so "MITRE OVAL"
describes the lineage rather than the current maintainer.)

The contrast is what makes the point, and it comes from a product rather than a
standard. In the AWS Security Hub finding format, `Compliance.Status` is
`PASSED | WARNING | FAILED | NOT_AVAILABLE`, and the AWS service model
documents the last one as:

> `NOT_AVAILABLE` — Check could not be performed due to a service outage, API
> error, or because the result of the Config evaluation was `NOT_APPLICABLE`.
> If the Config evaluation result was `NOT_APPLICABLE` … Security Hub CSPM
> automatically archives the finding after 3 days.
>
> — `botocore/data/securityhub/2018-10-26/service-2.json`, `Compliance`

Three unrelated conditions in one value — the monitoring broke, the API broke,
or the rule does not apply here — with the consequence that a collector outage
inherits the disposal policy of an irrelevant rule. That is the collapse OVAL
refuses to make, in a product a security team is more likely to have in front
of them than a SCAP document.

Behavioural detection has no defence against it at all. "No anomalies for this
agent" and "we had no usable telemetry for this agent" render identically on
every dashboard in the stack above — including Cohaera's own, before the
coverage contract was built. Cohaera ports the OVAL distinction to agent
telemetry: every check publishes what it required, what it got, what was
missing, a stable reason code and a remedy. `TOOL_CLASS_UNKNOWN`.
`NO_CAPABILITY_MANIFEST`.
`APPROVAL_BOUND_BY_SPAN_ONLY`. `EVENT_ORDER_INDETERMINATE`.
`POLICY_SEMANTICS_UNDECLARED`. The codes are stable because downstream
correlation content is expected to match on them.

The evaluation card contains one measurement of that idea earning its keep, and
it is the only result here I would defend without qualification. On the
unseen-vocabulary, name-only cell, the false positive rate *drops* to 15.3% and
precision *rises* to 62.5% — a swing a card reporting precision alone would
have published as an improvement. It is not one. Every check that needs to know
whether a call was consequential goes blind, because every tool classifies as
`unknown`. The detector got quieter by going dark, and the thing that makes
that visible is the coverage figure next to it falling from 0.62 to 0.13.

**A precision number that improves because the detector stopped being able to
see is the failure mode. A coverage contract is what catches it.**

That is transferable to ABA whether or not any of Cohaera's checks are any
good. An analytics layer that can distinguish "this agent behaved normally"
from "we could not evaluate this agent" is strictly better than one that
cannot, and none of the products in section 2's table currently expose that
distinction. Three things Cohaera could contribute, in decreasing order of how
much I would bet on them:

1. **A per-check coverage contract**, in the form above — required surfaces,
   present surfaces, missing surfaces, reason code, remedy — as a field on
   normalised agent events. This is a schema proposal, not a product, and it is
   the one worth taking.
2. **Evidence-integrity verdicts as correlation-ready features**: chain
   continuity, key trust and rotation, freshness, and exact argument binding of
   approvals and provider receipts to the calls they claim. Deterministic,
   explainable, and orthogonal to any baseline.
3. **An adversarial corpus and a published failure catalogue** that can be
   pointed at somebody else's detections, not only at Cohaera's.
   [EVASION.md](../EVASION.md) is 22 constructed evasions whose tests pass
   *while the evasion works*. Most of them are not specific to this
   implementation: E07 (act first, read untrusted content second), E08 (split
   across sessions), E12 (fragment the session id) and E13 (omit the event) are
   attacks on the observation model, and any behavioural layer reading the same
   telemetry inherits them.
