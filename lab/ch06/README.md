# CH06 conformance lab

> **Status: executed and committed.** The fixtures and results on this page are
> regenerated by `run.py --check`. They test the evidence-integrity contract;
> they do not measure detection of agent behaviour.

This lab answers one bounded question from the second-pass plan:

> Given a frozen collector stream and a known mutation, does Cohaera describe
> its integrity and coverage correctly, and how does that compare with a small
> sequence/hash-chain/signature verifier?

## Run it

From the repository root, with any supported Python 3.10–3.13:

```bash
python lab/ch06/run.py --check
```

Expected output:

```text
lab/ch06: 9/9 cases matches the committed matrix (...s, python 3.x)
```

Regenerate the committed fixtures and results after an intentional change:

```bash
python lab/ch06/run.py
git diff -- lab/ch06
python lab/ch06/run.py --check
```

## Experimental controls

- [`expectations.json`](expectations.json) is hand-written. `run.py` reads it
  but never generates or edits it.
- [`canonical.signed.jsonl`](fixtures/source/canonical.signed.jsonl) is the
  pristine recorder output. Every case starts as a deep copy of these bytes.
- Mutations are applied only after signing. The signed stream is never rebuilt
  to make a changed record look legitimate.
- The stream contains two sessions and crosses from `target` to `other` between
  sequences 2 and 3. This exercises attribution across a shared collector
  stream rather than only single-session examples.
- Each case gets fresh ledger state. `replayed` alone is submitted twice to the
  same retained ledger.
- [`baseline.py`](baseline.py) imports only the Python standard library. It
  independently implements canonical hashing, the stream chain, Ed25519
  verification and a small replay ledger; it imports no Cohaera modules.
- The published lab signing seed is for deterministic testing only. It provides
  no deployment trust.

## Matrix

| Case | Change after signing | Required interpretation |
|---|---|---|
| `intact` | none | fully verified |
| `deleted` | remove interior sequence 2 | manipulated, both boundary sessions affected |
| `modified` | change sequence 2 body | manipulated, `target` affected |
| `stripped` | change sequence 2 and remove `prev`/`chain` | manipulated, both boundary sessions affected |
| `reordered` | deliver 0, 2, 1, 3, 5, 4 | benign transport reordering |
| `truncated` | remove the final signed record | explicit incomplete attestation |
| `replayed` | submit the intact bytes twice | cross-run replay |
| `no_key` | omit the collector trust store | explicit missing prerequisite |
| `unsupported` | change the scheme to `cohaera.integrity:2` | explicit unsupported/not-evaluated result |

The committed [results](runs/latest/RESULTS.md) currently pass all nine cases:

- zero affected sessions in manipulated cases are `verified_complete`;
- zero intact or reorder-only sessions are inadmissible;
- both missing and unsupported prerequisites are explicitly declined or
  degraded;
- Cohaera and the baseline agree on every stream-level interpretation;
- Cohaera localises the body-only modification to `target`, and distinguishes
  the truncated stream's `target` verified prefix from `other`, whose records
  are only chained and unsigned.

## What this establishes

This is a deterministic conformance result. It establishes that CH06 handles
these nine declared stream shapes as specified and that the result is not an
accident of Cohaera's own chain implementation.

It does not establish that a real recorder sits outside an agent's writable
boundary, that a collector tells the truth, or that Cohaera detects prompt
injection or unsafe behaviour. Those require the later running-agent experiment
with an independently controlled tool gateway. The four-VM design in
[`LAB.md`](../../LAB.md) remains unnecessary for this stage.
